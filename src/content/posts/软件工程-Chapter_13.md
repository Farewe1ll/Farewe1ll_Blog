# 软件工程 Chapter 13 软件过程管理与改进

## 第十三章核心定位与逻辑脉络

### 核心定位

软件过程管理与改进是**组织级的软件工程保障体系**——在第十二章项目级管理的基础上，聚焦“组织层面的过程标准化与持续优化”，通过CMMI（组织级框架）、PSP（个体级过程）、TSP（团队级过程）构建“组织-团队-个人”三级过程体系，确保所有项目都遵循统一的规范流程，同时通过持续改进提升组织整体的软件开发能力（呼应第一章“工程化、规范化”核心，过程是质量与效率的长期保障）。

### 核心逻辑链

本章遵循“**组织级框架→个体级能力→团队级协同→过程认证**”的流程：

```
组织需求（统一流程+持续改进）→ 软件过程管理核心→ 能力成熟度模型（CMM/CMMI）→ CMMI过程域详解→ 个体软件过程（PSP）→ 团队软件过程（TSP）→ 过程标准认证（ISO9000/ITIL/SPICE）→ 组织过程优化闭环
```

核心目标：建立“可重复、可量化、可优化”的组织级软件过程，打破项目间的“孤岛效应”，通过过程改进实现质量、效率的持续提升。

## 软件过程管理核心认知

### 1. 核心定义与价值

- 软件过程管理：组织建立统一、明确定义的软件过程，让所有项目遵照执行，并在实践中持续改进的管理活动；

- 核心价值：

  1. 标准化：避免项目因个人习惯差异导致的质量波动；

  2. 可重复：成功项目的流程可复用，降低新项目风险；

  3. 可改进：通过过程数据量化分析，找到优化点，持续提升组织能力；

- 关键原则：无通用不变的过程，需根据项目领域、边界约束进行**裁剪定制**，平衡“规范”与“灵活”（呼应第一章“分而治之”“逐步求精”原则）。

### 2. 过程管理的核心平衡

软件过程需平衡四大核心要素，避免顾此失彼：

- 质量：过程需保障软件符合质量标准（如缺陷率、可用性）；

- 功能：过程需支撑需求的完整实现；

- 成本：过程需控制资源投入，避免过度规范导致的成本浪费；

- 时间：过程需优化流程效率，避免冗余环节导致项目延期；

- 关联前序章节：第十二章项目计划的“时间-成本-质量”三角，在组织级过程中通过标准化进一步平衡。

## 能力成熟度模型：从CMM到CMMI

能力成熟度模型是过程管理的核心框架，从CMM（能力成熟度模型）演进到CMMI（集成能力成熟度模型），核心是将组织的过程能力按成熟度分级，提供明确的改进路径。

### 1. CMM的五个成熟度等级（基础框架）

CMM将组织过程成熟度分为5级，等级越高，过程越规范、可预测：

| 成熟度等级 | 核心名称 | 核心特征 | 过程状态 | 典型实践 |
| :---: | :---: | :---: | :---: | :---: |
| 1级 | 初始级（Initial） | 过程无序，依赖个人能力，项目成功靠运气 | 混乱、不可预测 | 无统一流程，文档零散，缺陷率高 |
| 2级 | 已管理级（Managed） | 建立基本项目管理过程，跟踪成本、进度、质量 | 有基本规范，可跟踪 | 制定项目计划（WBS）、配置管理、质量控制 |
| 3级 | 已定义级（Defined） | 组织级过程标准化，项目可裁剪使用 | 标准化、可重复 | 建立组织级过程资产库、过程裁剪指南、技术评审流程 |
| 4级 | 已量化管理级（Quantitatively Managed） | 用数据量化过程和产品质量，可预测 | 量化、可控制 | 建立过程度量指标（如生产率、缺陷密度）、统计过程控制 |
| 5级 | 优化级（Optimizing） | 持续改进过程，通过数据识别优化点 | 持续优化 | 过程改进计划、标杆对比、创新实践引入 |

### 2. CMMI：CMM的集成与改进

- 核心改进：CMM仅关注软件，CMMI集成了软件、系统工程、集成产品开发等领域，适用范围更广；

- 过程域（PA）：CMMI的核心组成单元，即“做好软件开发某一方面的具体流程”，共22个过程域，按等级分布：

  - 2-3级：18个过程域（核心是项目管理、工程实践、支持过程）；

  - 4-5级：4个过程域（核心是量化管理、持续改进）；

- 改进示例：原组织的“项目任务分解”流程，按CMMI“需求开发”SP1.1改进后，新增“风险分析、技术准备、可重用部件识别”等环节，让流程更完整。

## CMMI过程域详解：结构与实践

每个CMMI过程域都有标准化结构，明确“要达成的目标”和“要执行的实践”，确保过程可落地、可检查。

### 1. 过程域的通用结构

| 结构模块 | 核心作用 | 说明 |
| :---: | :---: | :---: |
| 目的陈述 | 明确过程域的核心目标 | 回答“这个过程域要解决什么问题” |
| 简介 | 补充过程域的适用场景、核心活动 | 说明过程域的范围和关键动作 |
| 特定目标（SG） | 过程域必须达成的核心目标（不可裁剪） | 如“建立估算”“获得计划承诺” |
| 特定实践（SP） | 达成特定目标的具体动作 | 每个特定目标对应1~多个特定实践 |
| 通用目标（GG） | 所有过程域都需达成的基础目标 | 如“达成特定目标”“制度化过程” |
| 通用实践（GP） | 达成通用目标的具体动作 | 确保过程被执行、监控、改进 |
| 工作产品实例 | 实践产出的文档/数据 | 如WBS、估算报告、计划文档 |
| 子实践 | 特定实践的细化步骤 | 指导实践的具体执行细节 |

### 2. 示例：PP过程域（项目计划，Project Planning）

PP是CMMI 2级项目管理类核心过程域，核心是“建立并维护项目活动计划”，具体结构如下：

#### （1）基础信息

- 成熟度等级：2级；

- 过程域类型：项目管理类；

- 目的：建立并维护定义项目活动的计划，为项目执行与控制提供基础。

#### （2）特定目标与特定实践

| 特定目标（SG） | 特定实践（SP） | 子实践示例 | 工作产品实例 |
| :---: | :---: | :---: | :---: |
| SG1：建立估算 | SP1.1：估算项目范围 | 1. 制定顶层WBS；2. 定义工作包；3. 识别外部采购产品；4. 识别可重用工作产品 | WBS、工作包描述、任务描述 |
|  | SP1.2：估算工作量与成本 | 1. 基于历史数据估算；2. 考虑风险因素；3. 文档化估算依据 | 工作量估算报告、成本估算报告 |
| SG2：制定项目计划 | SP2.1：制定项目进度 | 1. 确定任务依赖；2. 分配资源；3. 设定里程碑 | 项目进度计划（甘特图） |
|  | SP2.2：制定支持计划 | 1. 配置管理计划；2. 质量保证计划；3. 测试计划 | 支持计划文档集 |
| SG3：获得对计划的承诺 | SP3.1：评审计划 | 1. 组织干系人评审；2. 解决评审问题 | 计划评审记录 |
|  | SP3.2：获得承诺 | 1. 明确职责分配；2. 相关方签署承诺 | 职责分配矩阵、承诺记录 |

#### （3）通用目标与通用实践

- GG1：达成特定目标：通过执行SP1.1~SP3.2，产出计划相关工作产品；

- GP1.1：执行特定实践：按子实践执行各特定实践，无需文档化过程描述（2级要求）；

- 关联前序章节：第十二章的WBS分解、项目计划、挣值分析，都是PP过程域实践的具体落地。

## 个体软件过程（PSP）：过程能力的个体落地

CMMI是组织级框架，而PSP（Personal Software Process）是针对**个体开发者**的过程体系，核心是让开发者通过标准化个人流程，提升工作质量和效率，为组织级过程提供个体能力支撑。

### 1. PSP的核心定位

- 本质：将组织级过程细化为个人可执行的步骤，让开发者“按过程工作”而非“凭感觉工作”；

- 与CMMI的关系：PSP是CMMI的个体补充，组织级过程最终需要通过每个开发者的实践落地；

- 核心价值：通过个人过程的度量（时间、缺陷），识别个人薄弱环节，持续改进（如减少编码缺陷、优化时间分配）。

### 2. PSP的三个成熟阶段（逐步提升）

| PSP阶段 | 核心目标 | 核心实践 | 能力提升 | 关联前序章节 |
| :---: | :---: | :---: | :---: | :---: |
| PSP0 | 理解软件过程思想，完成开发工作 | 1. 记录开发时间；2. 收集并分析缺陷；3. 按基本流程开发 | 从“无序开发”到“有记录的开发” | 第十一章缺陷跟踪、时间管理 |
| PSP1 | 计划个人工作，改进个人过程 | 1. 工作量估算；2. 制定个人进度计划；3. 分析过程改进点 | 从“被动执行”到“主动计划” | 第十二章项目计划、工作量估算 |
| PSP2 | 建立质量目标，自我评审 | 1. 制定个人质量目标（如缺陷率≤0.5/千行代码）；2. 编码后自我评审；3. 质量度量与分析 | 从“完成功能”到“保证质量” | 第十一章自我评审、质量度量 |

### 3. PSP的核心产出

- 个人过程数据：开发各阶段时间（需求分析、编码、测试）、缺陷发现与修复数据；

- 个人过程资产：个人编码规范、缺陷 checklist、估算经验库；

- 最终目标：培养“能自我管理、自我改进、保证质量”的开发者。

## 团队软件过程（TSP）：个体能力的团队协同

TSP（Team Software Process）是**团队级**的过程体系，核心是将CMMI的组织级管理要求与PSP的个体技能结合，打造高效协同的团队，确保团队按时交付高质量软件。

### 1. TSP的核心定位

- 本质：团队版的PSP，将个人过程整合为团队流程，解决“个体优秀但团队低效”的问题；

- 与CMMI/PSP的关系：CMMI提供“做什么”（组织要求），PSP提供“个人怎么做”（个体技能），TSP提供“团队怎么协同做”（团队流程）；

- 核心价值：通过团队过程的标准化，降低沟通成本、明确职责分工、提升协同效率。

### 2. TSP框架结构

TSP框架包含6个能力领域，覆盖团队从组建到项目交付的全流程：

| 能力领域 | 核心内容 | 关联实践 |
| :---: | :---: | :---: |
| TSP基础和原理 | 团队过程的核心思想、目标、原则 | 统一团队对过程的认知 |
| 团队基础 | 团队组建、角色分配、沟通机制 | 明确项目经理、技术负责人、开发/测试角色分工 |
| TSP的项目策划 | 团队WBS分解、工作量估算、进度计划 | 整合个人计划为团队计划 |
| TSP的项目实施和跟踪 | 团队任务跟踪、风险管控、过程监控 | 团队例会、进度偏差调整、风险协同应对 |
| 收集和使用TSP数据 | 团队过程数据度量、分析 | 统计团队生产率、缺陷密度、沟通成本 |
| 扩大TSP | 团队过程改进、经验沉淀 | 项目复盘、过程优化建议、资产库更新 |

### 3. TSP的核心目标

- 按时交付：通过协同计划和跟踪，确保项目进度可控；

- 质量达标：整合个人质量目标，实现团队整体质量要求；

- 成本可控：优化团队资源分配，避免冗余工作；

- 关联前序章节：第十二章的团队管理、风险管控，第十一章的团队测试，都是TSP的核心实践落地。

## 过程标准认证：过程合规性的外部验证

当组织过程满足特定标准后，可通过认证证明过程的合规性和成熟度，常见认证标准针对不同领域，核心是“以标准为依据，规范过程”。

### 1. 三大核心过程认证标准

| 认证标准 | 核心适用领域 | 核心特点 | 与CMMI的关系 |
| :---: | :---: | :---: | :---: |
| ISO9000 | 通用质量体系（适用于各行业） | 强调“质量体系的持续改进”，通用性强 | 与CMMI互补，ISO9000关注体系框架，CMMI关注软件过程细节 |
| ITIL | IT服务管理（如运维、服务交付） | 聚焦IT服务的流程标准化（如事件管理、变更管理） | 偏运维过程，CMMI偏开发过程，可结合使用 |
| SPICE | 软件过程改进与能力评估 | 类似CMMI，提供软件过程评估框架，更注重过程能力的定量评估 | 与CMMI属于同类标准，部分组织会选择其一作为评估依据 |

### 2. 过程改进的三个阶段

组织从“无过程”到“优质过程”，需经历三个阶段，最终内化为企业文化：

1. 僵化阶段：严格执行标准过程，即使不适应也先落地，建立过程意识；

2. 固化阶段：过程融入日常工作，成为团队习惯，无需刻意监督；

3. 优化阶段：基于过程数据，主动识别改进点，持续优化过程（呼应CMM 5级“优化级”）；

- 关联前序章节：第一章“持续改进软件工程实践”的原则，在组织级过程中体现为三阶段演进。
