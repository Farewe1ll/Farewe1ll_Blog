# 软件工程 Chapter 7 类的详细设计

## 第七章核心定位与逻辑脉络

### 核心定位

类的详细设计是**第六章代码框架到实际编码的关键衔接**，在第五章类设计（类-属性-方法-关系）和第六章代码生成（框架搭建）的基础上，聚焦“方法业务实现、状态行为描述、约束规则定义”，确保每个类的方法逻辑清晰、状态转换合规、业务规则无遗漏（呼应第一章“逐步求精”“结果可审查”的软件工程原则）。

### 核心逻辑链

本章遵循“**明确活动→工具支撑→行为描述→约束定义→落地编码**”的流程：

```
第六章代码框架 → 详细设计活动（算法/数据结构/物理设计）→ 方法设计（图形/表格/语言工具）→ 类状态描述（状态图）→ 业务规则约束（OCL）→ 编写详细设计说明书→ 评审→ 支撑最终编码实现
```

核心目标：让代码框架从“空壳”变为“可执行”，确保业务逻辑与第三章需求一致。

## 详细设计的主要活动：覆盖全维度细化

详细设计以第五章类图和第六章代码框架为基础，通过6大核心活动，完成“宏观设计→微观实现”的转化，每个活动都直接服务于编码落地。

### 1. 六大核心活动及作用

| 活动类型 | 核心职责 | 关联前后章节 | 示例（结合Project类） |
| :---: | :---: | :---: | :---: |
| 算法设计 | 细化类方法的业务逻辑，用工具描述处理流程（如“计算项目完成进度”的步骤） | 第五章定义方法签名，第六章生成方法框架，本章补充逻辑 | 用程序流程图描述`completePctCompute()`的计算步骤（遍历子项目→累加进度→加权计算） |
| 数据结构设计 | 明确模块内的具体数据类型（细化第五章的概念数据类型） | 第五章定义属性类型（如Collection），本章明确为ArrayList/HashSet | 第五章`subprojects : Collection(Project)`→ 本章细化为`private List<Project> subprojects` |
| 物理设计 | 确定数据库的存储格式、记录安排、存储方法（依赖具体数据库系统） | 关联第三章非功能需求（如数据存储效率），支撑数据持久化 | Project类的`projectNo`作为主键，存储为INT类型；`startPlanned`存储为DATE类型 |
| 其他设计 | 输入/输出格式、人机对话设计（如实时系统的交互流程） | 第三章的交互需求、边界类设计（第五章） | 设计“项目工作量修改”的输入界面格式（数值输入框+确认按钮），限制输入为正整数 |
| 编写详细设计说明书 | 汇总所有设计细节，作为编码、测试的依据 | 呼应第一章“文档化”原则，为后续维护提供参考 | 包含类方法的算法流程图、数据结构定义、数据库表结构、界面原型 |
| 评审 | 验证算法逻辑、数据结构、物理设计的合理性 | 呼应第一章“阶段评审”原则，提前发现设计缺陷 | 评审`testEffortModification()`的算法是否覆盖所有边界情况（如工作量为0、超出父项目剩余额度） |

### 2. 核心原则

- 一致性：设计需与第五章类图、第六章代码框架保持一致，不偏离需求；

- 可执行性：所有设计细节需能直接转化为代码（如算法步骤需具体到“循环子项目集合”“判断进度是否合法”）；

- 可维护性：设计文档清晰，便于后续修改（如算法流程图标注关键步骤，OCL约束单独管理）。

## 类方法的详细设计：结构化与工具选择

类方法的详细设计核心是“结构化程序设计”——仅用顺序、选择、循环三种控制结构，确保代码块“单入口、单出口”，简化逻辑、降低维护成本。具体通过三类工具实现，需根据业务场景选择。

### 1. 结构化程序设计核心要求

- 仅使用三种控制结构：顺序（步骤依次执行）、选择（if-else/switch）、循环（while/for/until）；

- 禁止随意跳转：仅在必要时使用goto/break/continue（如跳出深层循环）；

- 目标：算法流程可预测、易理解、易调试（呼应第六章代码的可维护性要求）。

### 2. 三类方法设计工具（对比选择）

#### （1）图形工具：可视化流程（直观易懂）

| 工具类型 | 核心特点 | 优势 | 劣势 | 适用场景 |
| :---: | :---: | :---: | :---: | :---: |
| 程序流程图（Flowchart） | 用箭头表示控制流，包含开始/结束、处理、判断节点 | 简单直观、易于学习，适合新手 | 易出现随意跳转（破坏结构化） | 简单算法设计（如“判断项目是否可添加子项目”） |
| 盒图（NS图） | 用“盒子”嵌套表示控制结构，无箭头跳转 | 强制结构化，逻辑清晰 | 复杂逻辑绘制繁琐（多层嵌套） | 中小型模块的算法设计（如“项目任务添加”） |
| 问题分析图（PAD） | 二维树形结构，自上而下、自左向右展开 | 结构清晰、易翻译为代码，支持逐步细化 | 不适合描述非结构化逻辑 | 复杂算法设计（如“项目完成进度加权计算”） |

#### （2）表格工具：处理多条件组合（精准无歧义）

适用于“判断条件多、组合复杂、决策方案多”的场景，避免逻辑遗漏。

##### ① 判定表（决策表）

- 核心构成：4部分组成（条件列表→条件组合→动作列表→动作入口）；

- 关键逻辑：n个条件（每个有2种取值）对应2ⁿ种组合，每种组合映射唯一动作；

- 化简技巧：用“-”表示“不关心该条件”，合并重复规则（如“功率>50马力”和“运行>10年”都对应“送外维修”，可合并）；

- 示例：机器维修决策（功率、运行时长、维修记录→维修方式）。

##### ② 判定树（决策树）

- 核心定位：判定表的“可视化变种”，用树结构表示条件与动作的对应关系；

- 优势：比判定表更易理解（尤其条件取值多于2种时，如功率分“<20”“20~50”“>50”）；

- 适用场景：条件组合多但需直观展示的场景（如“用户登录验证”：用户名是否正确→密码是否正确→是否记住登录→登录结果）。

#### （3）语言工具：伪代码（PDL）—— 连接设计与编码

- 核心定义：PDL（Programming Design Language）是“类编程语言+自然语言”的混合工具，无语法错误但不可执行，仅用于描述算法逻辑；

- 核心特点：

  1. 固定关键字（如if/else/while/for），遵循结构化控制结构；

  2. 大量使用自然语言描述业务逻辑（如“查询子项目的完成进度”）；

  3. 逐步细化（从粗逻辑到细步骤）；

- 示例（Project类的`addSubproject`方法PDL）：

  ```
  PROCEDURE addSubproject(subproj: Project)
    // 前置条件：子项目编号非空且不重复，父项目未结题
    IF subproj.projectNo IS NULL THEN
      抛出异常("子项目编号不能为空")
    ENDIF
    IF self.subprojects.contains(subproj) THEN
      抛出异常("子项目已存在")
    ENDIF
    IF self.status = "已结题" THEN
      抛出异常("已结题项目不能添加子项目")
    ELSE
      self.subprojects.add(subproj)
      调用 updateCompletePct() // 更新父项目完成进度
    ENDIF
  END PROCEDURE
  ```

- 核心价值：直接映射为代码（将PDL的自然语言替换为具体编程语言语法，如Java的`list.add()`），降低编码难度。

## 类的状态描述：状态图（有状态对象的行为建模）

第五章定义的类分为有状态对象（如Project、电机控制器）和无状态对象（如工具类），状态图用于描述有状态对象的“生命周期行为”——即对象在不同状态下的响应逻辑，补充类图无法体现的动态行为。

### 1. 状态图的基本结构

#### （1）核心元素

| 元素类型 | 作用 | 示例（Project类） |
| :---: | :---: | :---: |
| 伪状态 | 开始状态（唯一）、结束状态（可多个） | 开始状态→“新建项目”，结束状态←“项目结束” |
| 状态 | 对象的行为模式，包含entry（进入动作）、do（保持动作）、exit（离开动作） | “项目计划”状态：entry→初始化计划数据，do→等待子项目/任务添加，exit→校验计划完整性 |
| 状态转换 | 触发条件（事件+可选条件）+ 动作 | 事件“添加子项目”+ 条件“项目未结题”→ 从“项目计划”转换到“项目计划”（自转换），动作→调用`addSubproject()` |

#### （2）核心规则

- 状态转换是“确定性的”：同一事件+条件仅对应一个目标状态（避免逻辑歧义）；

- 动作执行顺序：转换动作→目标状态的entry动作（如“添加子项目”动作执行后，再执行目标状态的entry动作）。

### 2. 状态图的扩展（应对复杂对象）

当对象状态较多时，需通过“复合状态”“并行状态”简化描述，避免状态图过于臃肿。

#### （1）复合状态：状态嵌套

- 核心逻辑：将多个关联子状态组合为“复合状态”，共享公共转换（如所有子状态都响应“项目取消”事件，直接转换到“项目结束”）；

- 示例：Project类的“活动项目”是复合状态，包含“项目计划”“项目执行”子状态，两者都可通过“结题”事件转换到“项目结束”。

#### （2）并行状态：独立子状态图

- 核心逻辑：对象状态由多个互不依赖的子状态构成，每个子状态图独立描述一种行为（如时钟的“时间显示”和“日期显示”是并行状态）；

- 关键规则：

  1. 事件需在所有子状态图中处理，或触发统一转换；

  2. 离开复合状态时，所有子状态图同步结束；

- 示例：电机控制器的“运转状态”包含“负载状态”和“温度状态”两个并行子状态，分别描述负载变化和温度监控。

### 3. 状态图的适用场景

- 有状态对象的生命周期描述（如Project类：新建→计划→执行→结题→结束）；

- 交互密集型对象的行为（如界面类：初始界面→登录→应用运行→退出）；

- 实时系统的状态响应（如电机控制器：静止→启动→运转→待机→停止）。

## 对象约束语言（OCL）：复杂业务规则的精准定义

第五章的类图仅能描述“类-属性-方法-关系”，无法体现复杂业务规则（如“项目不能以自身为子项目”“学生选课数量≤12门”），OCL（Object Constraint Language）作为补充，专门描述这类约束，确保业务规则无遗漏。

### 1. OCL的核心定位与特点

- 核心作用：补充类图的不足，精准描述业务规则、前置条件（方法执行前）、后置条件（方法执行后）；

- 关键特点：

  1. 声明式语言：仅描述“是什么”，不描述“怎么做”（不能直接翻译为代码，但能指导编码）；

  2. 无副作用：不修改对象状态，仅做条件判断；

  3. 与UML无缝集成：可直接关联类、属性、方法。

### 2. OCL的基本语法与示例

#### （1）核心关键字

| 关键字 | 作用 | 示例 |
| :---: | :---: | :---: |
| context | 指定约束关联的UML元素（类、属性、方法） | `context Student`（约束学生类） |
| inv | 不变式约束：所有对象必须永久遵守 | `inv: self.stuId >= 10000`（学号≥10000） |
| pre | 前置条件：方法执行前必须满足 | `pre: self.freesemester = false`（未休学才能选课） |
| post | 后置条件：方法执行后必须满足 | `post: self.selectedLectures() > 0`（选课数>0） |
| self | 引用context关联的对象（类似Java的this） | `self.selectedLecture->size() <= 12`（当前学生的选课数≤12） |

#### （2）常用约束场景示例

##### ① 属性约束（类图补充）

- 需求：学生学号至少5位，≥10000；

- OCL：`context Student inv: self.stuId >= 10000`。

##### ② 方法前置/后置条件

- 需求：未休学学生选课方法执行前需未休学，执行后选课数+1；

- OCL：

  ```
  context Student::registerLecture(v: Lecture)
  pre: self.freesemester = false and not self.selectedLecture.contains(v)
  post: self.selectedLecture->size() = self.selectedLecture->size()@pre + 1
  ```

  （@pre表示方法执行前的状态值）

##### ③ 集合约束（多对象关联）

- 需求：学生本学期运行中的课程≤12门；

- OCL：

  ```
  context Student inv:
  self.selectedLecture->select(s | s.status = Lecturestatus::running)->size() <= 12
  ```

  （->select()筛选集合元素，->size()获取元素数量）

##### ④ 条件约束（implies）

- 需求：结课课程的成绩在1~5分之间；

- OCL：

  ```
  context Examination inv:
  self.selectedLecture.status = Lecturestatus::closed implies (self.note >= 1.0 and self.note <= 5.0)
  ```

  （implies表示“如果-则”逻辑）

### 3. OCL的核心价值

- 避免业务规则遗漏：将“隐性需求”（如学号规则、选课限制）显性化；

- 指导编码：开发人员可根据OCL约束编写校验逻辑（如在`registerLecture`方法中添加选课数量校验）；

- 便于评审：约束规则统一管理，评审时可快速验证是否符合第三章需求。
