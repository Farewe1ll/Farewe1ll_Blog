# 软件工程 Chapter 3 需求分析

## 需求分析核心定位与目标

### 核心定义

需求分析是软件开发的**输入源头**，核心目标是明确“用户真正想要的系统是什么”以及“存在哪些约束条件”。它是连接用户需求与技术实现的桥梁，直接决定后续开发的方向——“垃圾入，垃圾出”，需求分析的偏差会导致整个项目“失之毫厘，谬以千里”（呼应第1章软件危机中“需求理解偏差”的核心原因）。

### 核心任务

1. 捕获与描述需求：明确用户的显性需求（直接提出）与隐性需求（未明确但必需）；

2. 细化需求：将模糊的用户需求拆解为可执行、可验证的系统需求；

3. 区分需求类型：明确功能性需求（系统能做什么）与非功能性需求（系统要达到什么标准）；

4. 为后续开发提供依据：需求分析的成果是设计、编码、测试的核心输入。

## 需求分析的核心挑战

需求分析是软件开发上游的关键环节，其无序性是项目失败的重要诱因，核心挑战集中在3个方面，且相互关联：

### 1. 领域认知壁垒

- 开发人员需快速学习未知业务领域，不仅是记录信息，更要深入理解业务逻辑（如医疗系统需懂医疗流程、金融系统需懂风控规则）；

- 领域专家往往只掌握局部信息，难以全面预知哪些细节会影响开发（如财务人员可能忽略报表导出的格式对系统接口的要求）。

### 2. 需求动态变化

- 客户需求可能在开发中无征兆变更（如市场变化、业务调整）；

- 静态的分析方法难以应对动态需求，若未建立应对机制，会导致后期变更成本激增（呼应第1章“开发链条放大效应”，早期需求偏差后期修正成本指数级增长）。

### 3. 沟通与表达偏差

- 隐含假设：领域专家会遗漏自己熟悉的基础信息（如默认“库存不足时自动报警”，却未明确“库存临界值”）；

- 模糊表述：使用“大概”“通常”等词汇，缺乏精确性（如“报表要快”未说明“响应时间≤3秒”）；

- 术语歧义：不同角色对同一术语的理解不同（如“项目”在业务方指“业务项目”，在开发方可能指“开发任务”）。

## 需求分析的起点：可行性分析与需求分类

### 1. 可行性分析的双重作用

需求分析初期需伴随简短的可行性分析，核心产出：

- 技术+经济+社会可行性结论：判断项目“能否做、值得做”；

- 初步开发费用估算：作为与客户签订商务合同的依据（呼应第2章软件定义时期的“可行性分析”阶段，保持生命周期一致性）。

### 2. 用户需求与系统需求的区分

需求分析会产出两类核心文档，二者是“粗→细”的递进关系：

| 需求类型 | 主导方 | 阅读对象 | 核心特点 | 举例 |
| :---: | :---: | :---: | :---: | :---: |
| 用户需求（业务需求） | 客户/委托方 | 委托方/客户 | 宏观、原则化、偏业务语言 | “需要一个库存管理系统，能统计零件库存” |
| 系统需求 | 开发者 | 开发团队（设计、编码、测试） | 细化、可执行、偏技术语言 | “系统需支持零件入库/出库录入，库存低于临界值时自动生成订货单” |

### 3. 两类需求的核心共性

无论哪种需求，调研时必须先明确两个基础问题（为后续涉众识别、系统目标定义铺垫）：

- 项目的主要目标人群（谁用这个系统？）；

- 项目的核心目标（系统要解决什么问题？）。

## 涉众识别：需求的“来源主体”

### 核心定义

涉众（Stakeholder）是与目标系统相关的**一切人和物**，他们的期望直接影响系统设计。涉众可能是需求提出者、使用者、出资方，甚至是法律法规（间接约束），且重要程度不同——需优先满足核心涉众需求（呼应第2章敏捷开发“客户合作”的核心价值观）。

### 常见涉众类型及核心关注点

| 涉众类型 | 典型角色 | 核心关注点（需求来源） | 调研优先级 |
| :---: | :---: | :---: | :---: |
| 最终用户（直接涉众） | 操作员、业务员 | 操作便捷性、业务流程匹配度（细节需求） | 高（直接使用系统） |
| 投资者/出资方 | 企业老板、投资方 | 总成本、建设周期、投资回报（高层目标） | 高（决定项目是否推进） |
| 业务提出者 | 业务高层（总经理、部门经理） | 业务规范提升、效率优化（纲领性需求） | 中（需求原则化，需细化） |
| 业务管理者 | 中层管理者（科室主任） | 业务流程可控、数据可追溯（实际业务需求） | 高（熟悉业务细节，核心调研对象） |
| 业务执行者 | 一线员工 | 操作简化、减少重复工作（具体操作需求） | 中（需求可能不合理，可引导） |
| 其他涉众 | 第三方系统、法律法规 | 接口兼容性、合规性（约束条件） | 中（隐性需求，需主动挖掘） |

### 涉众管理核心原则

1. 准确识别：避免遗漏关键涉众（如忽略“法律法规”可能导致系统合规风险）；

2. 优先级排序：聚焦核心涉众的核心需求，避免“面面俱到”导致需求蔓延；

3. 协调斡旋：当涉众需求冲突时（如投资者要“低成本”，用户要“高功能”），需平衡各方期望。

## 系统目标：需求的“核心导向”

### 核心定位

系统目标是需求分析的“纲领”，与涉众识别紧密关联——目标决定了涉众的存在意义，涉众的期望又反过来细化目标（形成“涉众→目标→需求”的推导链）。

### 系统目标定义要求

1. 明确可验证：不能模糊表述，需说明“如何判断目标是否达成”（如“提升库存管理效率”需细化为“出库录入时间从10分钟/单缩短至2分钟/单”）；

2. 内部一致：目标之间无矛盾（如“低成本”与“高并发”需平衡，不能同时要求“零成本”和“支持10万用户同时在线”）；

3. 关联需求：所有用户需求都需与系统目标挂钩，避免“无目标的冗余需求”（如目标是“库存管理”，则“员工考勤”需求无需纳入）。

### 系统目标定义模板（直接落地使用）

| 模板字段 | 填写说明 | 示例 |
| :---: | :---: | :---: |
| 目标 | 明确、可量化的系统核心价值 | 实现零件库存自动监控与订货提醒 |
| 满足的期望 | 对应涉众的核心诉求 | 减少仓库管理员手动统计工作量，避免零件缺货 |
| 对涉众的影响 | 哪些涉众会受益/受约束 | 仓库管理员：工作量减少；采购员：及时获取订货清单 |
| 边界条件 | 目标实现的约束（时间、成本、技术） | 成本≤10万元，3个月内上线，兼容现有库存Excel表格 |
| 依赖 | 与其他目标的关系 | 依赖“零件信息录入”目标，二者相辅相成（无信息录入则无法监控） |
| 其它 | 补充说明（如风险、例外情况） | 若现有Excel表格格式不统一，需先进行数据清洗 |

## 系统功能识别：从“目标”到“用例”

### 核心逻辑

系统功能是系统目标的“具体落地”，识别功能的核心思路是“从涉众需求出发，结合业务流程，提炼可执行的系统动作”（呼应第2章用例驱动开发的思想）。

### 功能识别的5种核心方法

| 方法 | 适用场景 | 核心优势 |
| :---: | :---: | :---: |
| 座谈法 | 需明确业务工作流程（如采购流程、审批流程） | 快速获取整体业务逻辑，多方共识 |
| 关键涉众访谈 | 核心功能确认（如投资方、业务高层关注的功能） | 精准把握核心需求，避免偏离目标 |
| 调查问卷 | 大范围用户的共性需求（如终端用户的操作习惯） | 覆盖广，数据客观 |
| 旧系统分析 | 系统升级/替换项目 | 挖掘现有问题与优化点，降低用户学习成本 |
| 现场调研（On Site） | 终端用户操作场景明确（如仓库管理员入库操作） | 理解实际操作痛点，让用户融入开发过程 |

### 功能识别的辅助资源

除了直接调研，还可通过间接资源补充：领域专家、领域书籍、现有软件及文档、行业网站等——核心是快速学习业务术语与背景，避免因“不懂业务”导致功能识别偏差。

## 用例（Use Case）：需求的动态化描述

### 核心定义

用例（又称“用户故事”）是通过“角色与系统的交互场景”来捕获需求的工具，核心是“动态描述”而非静态说明——强调参与者的活动流程，而非单纯罗列功能（呼应第2章UML建模中“用例图是需求驱动核心”的思想）。

### 用例的核心要素

1. 角色（Actor）：系统边界之外与系统交互的对象，可是人（如仓库管理员）或其他系统（如“零件目录系统”“定时器Timer”）；
   - 注意：角色是“功能角色”而非具体的人（如“仓库管理员”是角色，张三、李四都可扮演该角色）；

2. 用例（椭圆表示）：角色与系统交互的“完整业务场景”，需能为角色创造价值（如“零件入库”“库存统计”）；

3. 关系：一个角色可对应多个用例（如仓库管理员可执行“入库”“出库”“库存查询”），一个用例可对应多个角色（如“项目状态分析”需项目经理和质量保证共同参与）。

### 用例识别的4个实用步骤（从易到难）

#### 步骤1：从核心业务实体出发（基础用例）

- 识别业务核心概念（如“零件”“项目”“员工”），每个实体对应5个基础用例（可合并/调整）：

  1. 创建实体数据（如“新建零件记录”）；

  2. 修改实体数据（如“修改零件信息”）；

  3. 删除实体数据（如“删除无效零件”）；

  4. 存储实体数据（如“零件数据入库”）；

  5. 访问实体数据（如“查询零件库存”）。

#### 步骤2：从动态过程数据出发（流程用例）

- 识别围绕核心实体的“变化过程”（如“项目组组建”“工作时间更新”），这些过程数据会频繁变化，需对应具体用例（如“项目团队组建”“项目安排更新”）。

#### 步骤3：从数据利用与分析出发（增值用例）

- 基于基础数据的“深度加工”（如“项目状态分析”“库存预警”），这类用例能为涉众创造额外价值（如通过分析项目数据得出“延期风险提醒”）。

#### 步骤4：从系统交互出发（接口用例）

- 分布式环境中，与其他系统的交互需单独用例（如“与财务系统对接”“定时器触发库存统计”）。

### 业务用例与系统用例的区分（避免混淆）
| 用例类型 | 视角 | 核心描述 | 范围 | 示例 |
| :---: | :---: | :---: | :---: | :---: |
| 业务用例 | 客户/业务方 | 业务流程（含手工+自动化） | 超越系统边界 | “采购流程”（含手工洽谈、系统录入、人工审批） |
| 系统用例 | 开发方 | 计算机系统的交互过程 | 系统边界内 | “零件入库录入”（仅系统内的操作流程） |

## 用例规约：用例的标准化文档

### 核心定位

用例规约是用例的“详细说明书”，将动态交互场景转化为“可执行、可验证”的文字描述，是开发、测试的直接依据——与用例图（可视化）配合，形成“图+文”的完整需求描述（呼应第2章UML建模中“图是窗口，模型是核心”的思想）。

### 用例规约完整模板（分两部分）

#### 第一部分：基础信息（定位用例）

| 字段 | 填写要求 | 示例 |
| :---: | :---: | :---: |
| 用例名称 | 动宾短语，简短精炼 | 零件入库录入 |
| 用例编号 | 项目内唯一编号（如UC-库存-001） | UC-STOCK-001 |
| 包 | 归属的业务子系统（用UML包封装） | 库存管理子系统 |
| 维护者 | 创建/维护该用例的人员 | 张三（需求分析师） |
| 版本 | 版本号+变更记录 | V1.0（2024-09-18 张三：初始创建） |
| 简介 | 一句话说明用例功能 | 仓库管理员录入零件入库信息，更新库存清单 |
| 参与的角色 | 执行该用例的角色 | 仓库管理员 |
| 业务支持者 | 解答用例疑问的业务人员 | 仓库主管（李四） |
| 引用 | 关联的规则/文档（如行业标准、旧系统文档） | 《仓库管理规范V2.0》 |

#### 第二部分：流程与需求（核心内容）

| 字段 | 填写要求 | 示例 |
| :---: | :---: | :---: |
| 前置条件 | 执行用例前系统必须满足的状态 | 仓库管理员已登录系统，零件信息已维护 |
| 后置条件 | 用例执行后的系统状态 | 库存清单中该零件数量增加，入库记录存档 |
| 基本事件流 | 正常执行的步骤（按顺序） | 1. 仓库管理员选择“零件入库”功能；2. 输入零件编号；3. 系统查询零件信息并显示；4. 录入入库数量、供应商；5. 点击“提交”；6. 系统更新库存并提示“入库成功” |
| 备选事件流 | 异常/特殊情况的处理 | 备选流1：输入无效零件编号→系统提示“零件不存在”→返回步骤2；备选流2：入库数量为0→系统提示“数量不能为空”→返回步骤4 |
| 关键性 | 用例的重要程度（高/中/低） | 高（核心库存管理功能） |
| 关联用例 | 相关的其他用例 | 包含“系统登录”用例，关联“零件信息查询”用例 |
| 功能需求 | 从用例派生的具体功能 | 1. 支持零件编号模糊查询；2. 入库数量需为正整数；3. 自动记录入库时间 |
| 非功能需求 | 派生的非功能要求 | 1. 提交响应时间≤1秒；2. 支持批量录入（单次≤10条） |

## 用例关系：包含与扩展（优化用例设计）

### 核心目的

当多个用例存在重复流程或特殊场景时，通过“包含”“扩展”关系复用逻辑，避免用例规约冗余（呼应第1章软件工程“复用”的核心思想）。

### 1. 包含关系（`<<Include>>`）：强制复用

- 核心逻辑：一个主用例**必须依赖**某个基础用例才能完成，基础用例提供“通用功能”；

- 关键特征：无条件发生（只要主用例执行，包含的用例就会执行）；

- 示例：“零件入库”“零件出库”“库存查询”都包含“系统登录”用例——所有功能都需要先登录；

- 注意：被包含用例是“完整任务”，不能是简单的逻辑分解（如不能把“零件入库”拆分为“输入编号”“输入数量”两个包含用例）。

### 2. 扩展关系（`<<Extend>>`）：条件复用

- 核心逻辑：一个主用例在**特定条件下**可选择执行某个扩展用例，扩展用例提供“特殊功能”；

- 关键特征：有条件发生（满足约束条件才执行），不影响主用例核心流程；

- 示例：“项目状态分析”用例扩展“项目警告”用例——只有“项目处于较差状态”（条件）时，才触发警告功能；

- 与包含关系的核心区别：包含是“必须有”，扩展是“可选有”。

### 用例优化原则

1. 用例粒度一致：同一用例图中的用例需处于同一抽象级别（如不能同时放“系统登录”和“零件入库批量处理”）；

2. 数量控制：每个用例图的用例数≤15个，避免过于复杂；

3. 用例的落地价值：可作为成本估算、迭代计划、团队分工的基础（呼应第2章敏捷开发“增量交付”的思想）。

## 活动图：用例流程的可视化建模

### 核心定位

活动图是UML中用于**描述过程流程**的工具，完美匹配用例规约的“基本事件流”和“备选事件流”——将文字步骤转化为直观图形，降低开发、测试人员的理解成本（与用例规约形成“文图互补”）。

### 活动图核心元素与语法

| 元素 | 作用 | 示例 |
| :---: | :---: | :---: |
| 开始点/结束点 | 标记流程的起点与终点 | 圆形（开始）、环形（结束） |
| 动作（Action） | 流程中的具体操作 | “录入入库数量”“查询零件信息” |
| 分支/汇聚 | 处理条件判断（分支）或多流程合并（汇聚） | 菱形，标注条件（如“[零件存在]”“[零件不存在]”） |
| 并行分支 | 多个动作同时执行（用“{and}”标记） | “选定项目经理”与“选定项目成员”并行执行 |
| 对象 | 流程中涉及的数据/实体（标注状态） | “Eclipse项目[已创建]”“入库单[已提交]” |
| 泳道（Swimlane） | 按角色/部门划分流程责任 | 编辑部流程中“作者”“编辑”“专家”各自的动作区域 |

### 活动图建模步骤（与用例规约联动）

1. 提取用例规约的“基本事件流”，每个步骤对应一个“动作”；

2. 标记动作的执行角色（用泳道区分）；

3. 补充“备选事件流”对应的分支条件与动作（如异常处理）；

4. 若某个动作复杂，可拆分为单独的子活动图（用特殊符号标记）；

5. 验证流程完整性：确保所有基本流、备选流都被覆盖，可作为测试用例设计的依据（呼应第2章软件测试“测试用例源于需求”的思想）。

### 示例：采购流程活动图逻辑

```
开始 → 销售代表访谈客户→ 确定具体需求 → 相关部门成本核算（分支：[常规开发]→常规成本核算；[定制开发]→定制化成本核算）→ 销售主管与客户洽谈（分支：[达成共识]→签订合同；[未达成共识]→重新核算成本）→ 结束
```

## 传统功能分析：数据流图（DFD）

### 核心定位

数据流图是**传统结构化方法**中的需求分析工具，与UML活动图的“流程可视化”不同，它聚焦“信息流的变换过程”——描绘数据从输入到输出的流动、存储、处理环节，适合纯功能型系统（如库存管理、工资计算）。

### 数据流图4大核心元素

| 元素 | 符号 | 作用 | 示例 |
| :---: | :---: | :---: | :---: |
| 外部实体 | 矩形 | 数据的源点/终点（系统边界外的对象） | 仓库管理员、采购员、银行 |
| 处理（加工） | 圆角矩形 | 对数据的变换（如计算、分类、存储） | “处理出入库单”“生成采购报表” |
| 数据存储 | 平行线/矩形（带缺口） | 数据的持久化存储（如数据库、文件） | “库存清单”“订货信息表” |
| 数据流 | 箭头 | 数据的流动方向（标注数据名称） | “出入库单”“需订货零件数据” |

### 数据流图分层画法（核心原则：从粗到细）

数据流图采用“分层细化”的方式，确保复杂系统的可读性，且需保持“层间一致性”（上层的处理对应下层的子流程）：

1. 0级数据流图（上下文图）：最抽象级别，仅展示系统整体与外部实体的交互（如“出入库管理系统”与仓库管理员、采购员的交互）；

2. I级数据流图：将0级的“系统”拆分为核心处理模块（如“处理出入库单”“产生报表”）；

3. II级及以上数据流图：进一步拆分I级的处理模块（如“处理出入库单”拆分为“出入库单录入”“更新库存清单”）。

### 数据流图绘制禁忌（避免错误）

1. 数据流不能是动词（如“入库”是动作，应改为“入库单数据”）；

2. 外部实体之间不能直接有数据流（必须通过系统处理）；

3. 处理必须有输入和输出（“无输入的处理”或“无输出的处理”都是无效的）；

4. 处理名称需是“具体及物动词+宾语”（如“处理出入库单”，不能是“数据处理”“信息管理”等空洞名称）。

### 数据流图与UML活动图的适用场景对比

| 工具 | 核心优势 | 适用场景 |
| :---: | :---: | :---: |
| 活动图 | 侧重“角色+流程”，可视化强，支持并行、分支 | 面向对象开发，需展示角色交互的流程（如用例流程） |
| 数据流图 | 侧重“数据变换”，逻辑清晰，适合分层细化 | 传统结构化开发，纯功能型系统，需明确数据流向（如库存、财务系统） |

## 需求的文字化导出：三类功能性需求

### 核心逻辑

无论是用例规约还是活动图、数据流图，最终都需导出“文字化的功能性需求”——这是需求说明书的核心内容，需满足“明确、可验证、无歧义”的要求（呼应需求分析“避免沟通偏差”的核心挑战）。

### 三类功能性需求（覆盖全场景）

| 需求类型 | 核心定义 | 示例 | 关联关系 |
| :---: | :---: | :---: | :---: |
| 系统功能需求 | 系统的核心业务功能（“能做什么”） | “系统需支持零件库存低于临界值时自动记录订货信息” | 核心类型，是其他两类需求的基础 |
| 交互需求 | 用户与系统的交互规则（“怎么用”） | “用户录入入库数量后，系统需实时校验是否为正整数” | 依附于功能需求，描述操作流程 |
| 外部接口需求 | 系统与其他系统/硬件的交互规则（“与谁交互”） | “系统需与财务系统对接，同步采购单数据” | 支撑功能需求，确保数据互通 |

### 文字需求模板（直接套用）

```
[需求编号] 需求名称：系统必须[动作] [目标对象]，[约束条件]（如时间、范围、格式）。
```

示例：R3.1 零件库存预警：系统必须在零件库存数量低于预设临界值时，自动记录该零件的编号、名称、当前库存到订货信息表中，记录时间精确到秒。

### 关键注意点

1. 术语统一：需维护“词汇表”，明确术语含义（如“项目”“子项目”在系统中的定义）；

2. 对应流程：每个动作、分支、判断都需对应至少一条需求（如活动图的“[零件不存在]”分支，需导出“系统需提示‘零件不存在’并返回重新输入”的需求）。

## 非功能性需求：软件的“质量保障”

### 核心定义

非功能性需求是对“软件质量特性”的要求，不直接描述系统功能，而是规定“功能要达到什么标准”——若忽略非功能性需求，即使功能满足，系统也可能因“不好用、不稳定”被弃用（如功能齐全但响应时间10秒，用户无法接受）。

### 非功能性需求的核心分类（基于ISO/IEC 9126标准）

| 质量特性 | 核心含义 | 示例 |
| :---: | :---: | :---: |
| 功能性（Functionality） | 系统是否能完成规定的功能 | “需支持批量录入10条入库记录” |
| 可用性（Usability） | 系统是否容易使用、学习、操作 | “新用户上手时间≤30分钟，操作步骤≤5步/单” |
| 可靠性（Reliability） | 系统是否稳定，无故障运行的能力 | “系统连续运行无故障时间≥720小时” |
| 效率（Efficiency） | 系统的响应速度、资源占用 | “入库单提交响应时间≤1秒，支持10人同时操作” |
| 可维护性（Maintainability） | 系统是否容易修改、扩展 | “新增零件类型时，无需修改核心代码” |
| 可移植性（Portability） | 系统是否能适配不同环境 | “支持Windows 10/11、Linux Ubuntu 20.04系统” |

### 非功能性需求的其他类型（约束条件）

1. 技术性需求：硬件要求（如“服务器CPU≥8核”）、软件平台（如“基于Java 17开发”）、运行环境（如“支持Chrome 90+浏览器”）；

2. 合同需求：商业条款（如“3个月内上线”“质保1年”）；

3. 交付物需求：除了软件，还需交付的文档（如《用户手册》《需求说明书》）、培训服务等。

## 需求分析的最终成果：需求说明书

### 核心定位

需求说明书是需求分析的**最终产出物**，是汇总所有分析结果的标准化文档——它是开发、测试、验收、维护的“共同依据”，也是应对需求变更的基础（呼应第2章“需求变更管理”的思想）。

### 需求说明书的核心结构（按顺序）

1. 文档说明性内容：版本号、创建者、修改记录、批准者（确保文档可追溯）；

2. 目标群体和系统目标：涉众分析结果、系统目标（含验证标准）；

3. 功能性需求：所有文字化的功能性需求（系统功能、交互、外部接口），关联用例、活动图、数据流图；

4. 非功能性需求：质量特性、技术性需求、合同需求等；

5. 交付物：明确交付的产品（软件、文档）、交付时间、交付形式；

6. 验收标准：需求的检验方法（如功能需通过多少条测试用例，响应时间需≤1秒）及结果处理方式；

7. 附件：词汇表（术语定义）、相关参考文档（如行业标准、旧系统文档）。

## 需求验证与跟踪：确保需求的有效性与一致性

### 需求验证：避免“无效需求”

需求验证的核心是检查需求是否“完整、一致、现实、可验证”，避免因需求本身缺陷导致后续问题：

| 验证维度 | 验证方法 |
| :---: | :---: |
| 一致性 | 自然语言描述→人工审查；形式化描述→软件工具校验（如需求冲突检测） |
| 现实性 | 结合开发经验判断；通过仿真、性能模拟验证（如“支持10万用户同时在线”是否可行） |
| 完整性与有效性 | 用户验证（核心涉众确认需求）；原型验证（快速原型演示，收集反馈） |

### 需求跟踪：应对“需求变更”

需求跟踪是将“源需求”与“后续产出物”（设计文档、代码、测试用例）建立关联，核心目的是：

1. 明确需求变更的影响范围（如修改“库存临界值”需求，需同步修改设计、代码、测试用例）；

2. 确保所有需求都被实现和测试（无遗漏需求）；

3. 逆向追溯：从代码/测试用例追溯到原始需求，明确修改的影响（呼应第1章“开发链条放大效应”，早期变更成本低）。

### 需求跟踪矩阵（RTM）：跟踪的核心工具

需求跟踪矩阵是实现需求跟踪的标准化表格，分为“纵向跟踪”和“横向跟踪”：

1. 纵向跟踪矩阵：

   - 需求派生关系：客户需求→系统需求→功能需求；

   - 实现与验证关系：需求→设计文档→代码模块→测试用例；

   - 责任分配关系：需求→负责开发/测试的人员；

2. 横向跟踪矩阵：需求之间的接口关系（如“零件入库”需求与“库存统计”需求的依赖关系）。

### 需求跟踪的价值（CMM三级要求）

- 需求变更管理：快速评估变更影响，避免“牵一发而动全身”；

- 测试完备性：确保所有需求都有对应的测试用例，无测试遗漏；

- 维护效率：后期维护时，快速定位问题对应的原始需求，降低维护成本。

## 需求分析全流程脉络总结（前后关联闭环）

需求分析是一个“从发散到收敛”的闭环过程，各环节层层递进、前后呼应：

```
涉众识别 → 系统目标定义 → 用例识别（业务用例+系统用例） → 用例规约编写 → 活动图可视化流程 → 导出三类功能性需求 → 数据流图补充数据流向 → 补充非功能性需求 → 编写需求说明书 → 需求验证（用户/原型确认） → 需求跟踪（建立RTM）
```

- 前承：呼应第1章软件危机的“需求理解偏差”“开发链条放大效应”，通过规范的需求分析流程解决核心问题；

- 后启：为第4章软件设计提供“明确、可执行”的输入，确保设计不偏离用户需求。
